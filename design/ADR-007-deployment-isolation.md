# ADR-007：部署隔离层级——不使用完整虚拟机（维持宿主机 + Docker 沙箱）

- **状态**：已接受（用户 2026-10-03 拍板"维持现状"）
- **日期**：2026-10-03

## 背景

用户提问："这个 Agent 有没有必要在虚拟机环境下运行？虚拟机里装模型会不会更好？"
需要正式评估三种"隔离"方案，因为它们常被混为一谈：

| 方案 | 隔离层级 | GPU（RTX 4060 8G） | 评估 |
|:--|:--|:--|:--|
| Docker 容器 | 进程级（共享内核） | 无需 | **已采用**（隔离 apktool 不可信面，方案 3.3） |
| WSL2 | 轻量虚拟机（Hyper-V） | ✅ CUDA in WSL2，性能损失 <5% | 备选（见下） |
| 完整 VM（VMware/VirtualBox） | 硬件级客户 OS | ❌ CUDA 无法直通 | **不采用** |

## 决策

**维持现状**：宿主机运行可信面（Ollama + Spring Boot 后端，仅监听本机），Docker 容器
仅隔离不可信面（apktool 解析不可信 APK：无网络/只读挂载/2C2G/120s 超时）。
**模型不装进虚拟机。**

## 理由

1. **威胁模型决定隔离层级**：本项目唯一的不可信执行面是"解析不可信 APK"（T4），
   已由 Docker 沙箱覆盖；Ollama/后端是自研可信代码、仅监听 localhost、不解析不可信
   二进制——给可信面套 VM 只增加复杂度，不增加安全收益。
2. **GPU 直通缺失（决定性）**：VirtualBox 不支持 CUDA 直通，VMware 的 GPU 加速仅限
   图形渲染。VM 内 Ollama 只能 CPU 推理（7B 约每秒个位 token），M9 性能指标
   （函数解释≤60s）必超，现场演示不可用。8G 显存是本机跑本地 LLM 的核心价值。
3. **嵌套复杂度**：apktool 沙箱依赖 Docker Desktop（Windows 下基于 WSL2 后端）。
   VM 内再套 Docker = 宿主机→VM→Docker→apktool 三层嵌套，性能与排障成本剧增。
4. **磁盘约束**：C 盘仅剩 32G，VM 虚拟磁盘（客户 OS+依赖+模型）需 30-60G。
5. **O6 交接**：B 组需在干净环境按 RUNNING.md 复现；几十 G 的 VM 镜像无法走 git
   仓库，恢复测试难度剧增。

## 备选方案（已评估、暂不启用）

- **WSL2 跑 Ollama**（类虚拟机折中）：宿主机更干净、可一键 `wsl --unregister` 重置，
  CUDA 性能接近原生，且与 Docker Desktop 共享同一 WSL2 后端。代价：默认预占一半
  物理内存（≤16G 内存的机器会紧张）、RUNNING.md 需改写、模型放 /mnt/d 挂载路径
  加载变慢。**启用条件**：宿主机内存 ≥32G 且明确要求 Windows 环境零污染时再切换，
  届时走 O5 Change 流程。
- **完整 VM 的真正用武之地**：恶意样本动态分析（需快照回滚，如 FLARE-VM 模式）——
  本项目方案 2.3 已明确列为非目标，不适用。

## 后果

- 正面：8G 显存全量用于推理；RUNNING.md 恢复流程最简单；架构无嵌套；
- 负面：Ollama/依赖直接安装在宿主机（可接受：均为官方安装包，且 reset.sh 可清数据）；
- 关联：RUNNING.md"部署形态"节；方案 3.3 节。
