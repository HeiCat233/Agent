# ADR-005：目录注释重写（DIRECTORY_REWRITE，FR-09）

- **状态**：已接受
- **日期**：2026-09-30
- **需求来源**：用户提出"逆向 Agent 对理解的文件目录有重写需求"；经确认采用
  **注释版目录树重写**方案（不做可读代码重写、不做修改性操作）。

## 背景

apktool 解码后的原始目录树庞大且不可读（混淆名、资源目录、多 dex），学习者很难
建立"目录→功能"的心智模型。需要把原始结构**重写**为一份面向学习者的注释版目录树。

## 决策

### 定位与边界

- **只读分析**：不重命名、不重打包、不触碰原样本；"重写"仅指输出层的重组与注释；
- 新增 `analysis_type = DIRECTORY_REWRITE`，复用 6 阶段管线的 Stage 1/2 产物。

### 生成流程（关键设计：规则优先，LLM 最小化）

1. **规则骨架（不经 LLM，天然可信）**：顶级包列表、每包类数量、Manifest 组件归属、
   `lib/*.so`、`assets/`、`res/` 的标准语义；
2. **LLM 受限注释**：仅对"包级用途推断"调用 LLM，输入=该包类名清单+Manifest 片段，
   同样以 `<untrusted_code>` 数据包裹（复用 ai_rules 四条铁律）；
3. **混淆名标注**：`a.b.c` 形式的包/类可给推断角色，**必须标 `inference=true`**
   并计入置信度扣分；
4. **关键文件高亮规则**：MainActivity / 自定义 Application 类 / `lib/*.so` /
   加固特征文件（厂商特征 so/配置）/ assets 下可疑配置；
5. **Stage 6 回验**：LLM 注释中出现的每个类名/文件路径逐一在 Stage 2 索引中验证，
   **失实注释直接删除**；全树置信度=注释证据覆盖率（规则计算）。

### 输出形态

Markdown 渲染的树 + 注释表；前端证据面板渲染并提供**导出 .md 按钮**。

## 备选方案（被否决的）

- **可读代码重写**（smali→Java 风格整文件重写）：幻觉风险与工作量显著更高，
  如后续需要，以 O5 Change 提案作为二期目标；
- **让 LLM 直接读整棵目录树生成注释**：上下文超限且引用无法回验，否决。

## 验收与指标

- R08：正向（白名单 APK → 注释树+引用可回验+可导出）；负向（非白名单 → REJECTED；
  混淆样本 → 注释降级+全部标注 inference，低于阈值 → UNCERTAIN）；
- 指标：注释树引用有效率 ≥95%（确定性比对索引）；用途注释准确率 ≥80%（双评）；
  混淆样本注释必须 100% 带 inference 标记。

- 威胁模型：复用 T1（注入串可能藏在 Manifest/资源名中）
